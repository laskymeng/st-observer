# 酒馆观测台复盘

读 st-observer 的录像带，复盘 SillyTavern 真机测试里发生的事，用大白话讲给用户听。

> **安装必读**：把本文件夹放进你的 agent skills 目录（Pi：`~/.pi/agent/skills/`），
> 然后把下面所有 `<你的 st-observer 文件夹>` 替换成你机器上的实际路径（如 `D:/tools/st-observer`）。

## 它是什么

观测台 = 摄像头 + 电话亭 + 录像带，三层各管一事：

- **摄像头**（observer.js）：装在酒馆助手脚本库里，纯只读旁观，零侵入、零 AI 算力消耗
- **电话亭**（phonebooth.py）：本地小接收器，监听 127.0.0.1:6701，负责把观测记录落盘
- **录像带**（logs/ 目录）：所有记录的存放处

使用循环：测前双击 `启动电话亭.bat`（黑窗口停住 = 录像机就位）→ 酒馆里正常玩（摄像头常驻录像）→ 测完说"看看记录"，本技能自动翻录像带复盘。

## 数据位置

- 主记录：`<你的 st-observer 文件夹>/logs/observe.log`（每行一条 JSON，含时间戳）
- 提示词全文：`<你的 st-observer 文件夹>/logs/prompts/*.txt`
- 项目交付物在 `<你的 st-observer 文件夹>/`（observer.js / phonebooth.py / 启动电话亭.bat / 使用说明书.md / 酒馆观测台_脚本包.json）

## 读取方法（重要，Windows 乱码坑）

- 日志是 UTF-8；Windows 终端（GBK）直接 print 中文必乱码
- 正确做法：用 Python 读取后**写入临时文件再 read 工具查看**，或输出用 `unicode_escape` 转义后人工还原
- 写 Python 脚本文件执行（heredoc 方式），不要用 `python -c` 或 `curl` 传中文参数
- 二进制读取：`open(path,'rb').read().decode('utf-8')` 最稳

## 五路核对框架

每轮复盘按这五路核对，逐项给结论：

1. **事件序列**：消息 id 是否连贯（从起始到最新逐轮递增）、生成开始/结束是否配对
2. **提示词快照**：最新文件大小（正常是几万字节）、抽取角色卡核心设定与当前剧情（system/character/世界书注入/最新剧情进展）、验证人设与机制是否正确注入
3. **世界书点亮**：点亮名单是否显示真实名字（不是 `?`）、是否为预期条目
4. **变量快照**：有无 undefined/null，MVU 变量（聊天/消息/角色/全局）是否按预期变化
5. **报错**：kind=error / unhandledrejection 记录，事件断链等异常

## 已知正常现象（别误报为 bug）

- `dry_run=true` 的生成开始：酒馆预演（不算 AI 算力），可能不发结束事件
- `type=quiet` 的生成开始：消息编辑等内部静默生成
- 同一 message_id 两条"生成结束"：消息更新/滑动二次触发
- 0 字节提示词文件：历史残留（旧版 bug 期产物），看最新的几个文件即可
- 提示词快照里出现大量对话历史是正常的（提示词本来就包含上下文）

## 制卡调试复盘（核心场景）

用户在写/改角色卡后测试，重点回答三个问题：

- 世界书点亮的是不是预期条目？名字是否真实？
- 提示词快照里人设/机制有没有正确注入？（读快照开头 3000 字符定位角色卡设定区）
- MVU 变量是否按预期变化？有无报错？

## 报告风格

- 用大白话 + 生活化比喻（摄像头/录像带/电话亭），术语首次出现要翻译
- 不要直接甩原始 JSON 给用户；整理成表格或要点
- 发现异常时：先说明现象 → 判断是 bug 还是"已知正常现象" → 给出下一步建议
- 报告末尾问一句"需要我帮你清理/过滤某类记录吗"（说一声再动手）
